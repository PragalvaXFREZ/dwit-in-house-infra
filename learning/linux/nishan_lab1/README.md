# Three Shells: Comparing Bash, Dash, and Python Shells

In this lab, I explored how different Unix shells work by comparing Bash, Dash, and two Python-based shells: `mysh.py` and `aish.py`. The main objective was to understand how shells execute commands, handle errors, manage processes, and support features such as pipes and input/output redirection.

First, I created a shell probe script to compare Bash and Dash. I tested features including `echo -e`, `$RANDOM`, brace expansion, single and double brackets, the `source` command, and Bash arrays. I learned that Bash supports several additional features that Dash does not. For example, Dash does not support Bash arrays or `[[ ]]`, and it uses the POSIX `.` command instead of `source`. I also learned why Debian commonly uses Dash as `/bin/sh`: it is lightweight and generally starts faster.

Next, I measured shell performance using a loop that ran 200,000 iterations and a startup test that launched each shell 300 times. In my initial loop measurements, Dash completed the task in approximately 0.192 seconds, compared with Bash at 0.429 seconds. In the startup test, the average times were approximately 0.342 seconds for Dash and 0.545 seconds for Bash. These results helped me understand the performance differences between the two shells.

I then built `mysh.py` in Python. It supports basic command execution, built-in commands such as `cd` and `exit`, pipes, input/output redirection, and Ctrl-C handling. I tested it using a battery of 12 tests. Most basic tests passed, including command execution, exit statuses, redirection, and interruption. However, I found that my shell could not correctly handle a pipeline containing multiple pipe operators, such as `printf ... | sort | uniq -c`. This helped me understand that implementing pipelines requires careful process management.

Finally, I tested `aish.py`, which was generated by an AI assistant. Although it passed the original 12-test battery, additional testing revealed a bug. When I ran `echo ">"`, the shell incorrectly treated the quoted `>` character as an output-redirection operator instead of ordinary text. The cause was that the `shlex` tokenizer removed quotation marks before the parser identified operators. As a result, the parser could no longer distinguish quoted characters from actual shell syntax. I fixed this by preserving quotes during tokenization and removing them only when processing normal arguments or filenames.

This lab taught me that building a shell involves much more than executing commands. It requires understanding processes, file descriptors, pipes, signals, parsing, and error handling. Most importantly, I learned that AI-generated code should not be trusted without independent testing. A program can pass its initial tests and still contain important bugs in less common situations.
